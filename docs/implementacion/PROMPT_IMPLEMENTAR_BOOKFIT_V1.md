# Prompt para implementar BookFit V1

Copia el bloque completo en el agente de código con acceso a este repositorio. Si el agente trabaja fuera del repositorio, adjunta también `PLAN_BOOKFIT_V1.md` y dale acceso al código.

~~~text
Implementa la primera versión funcional local de BookFit en el repositorio clientes_espacios. Lee AGENTS.md, docs/implementacion/PLAN_BOOKFIT_V1.md, README.md y los módulos existentes antes de editar. Usa el plan como especificación funcional y técnica. Implementa y comprueba el resultado en esta sesión. Puedes delegar revisiones de base de datos, API y seguridad a subagentes, coordinando sus cambios.

Conserva React, Vite, TypeScript y pnpm. Añade Fastify y node-postgres. El frontend se comunica con /api y Fastify controla permisos, precios, disponibilidad, reservas y pagos. Usa PostgreSQL mediante Supabase CLI y Docker en este ordenador. El ejemplo de Vue con una tabla todos corresponde a otro proyecto. Para esta fase, node-postgres cubre el acceso a datos y el SDK @supabase/supabase-js se reserva para cuando integremos Supabase Auth. Puedes consultar las guías de Supabase y PostgreSQL disponibles en el entorno.

1. Comprueba Node, pnpm, Docker y si hay una instancia local del proyecto. Reutiliza la configuración existente. Si falta, instala Supabase CLI como dependencia de desarrollo con pnpm e inicializa el directorio supabase/. Usa pnpm exec supabase start. Trabaja con la URL de PostgreSQL de la instancia local obtenida mediante pnpm exec supabase status. La URL y la clave publicable de Supabase Cloud compartidas previamente quedan reservadas para otra fase. Mantén la API y servicios locales fuera de la red pública. Usa .env.example con valores de ejemplo y guarda la conexión real de desarrollo en configuración local ignorada por Git y leída solo en el servidor.
2. Crea migraciones SQL versionadas en supabase/migrations y datos sintéticos reproducibles en supabase/seed.sql. Modela actores, roles e identidades futuras, profesionales, servicios, salas, horarios, pedidos, retenciones, reservas, plazas, pagos y solicitudes. Separa credenciales de migración y ejecución. Crea semillas suficientes para probar clientes, profesionales, gestores y doble rol, con salas y clases donde se puedan provocar conflictos de reserva. Comprueba las migraciones desde cero sobre una instancia local desechable con pnpm exec supabase db reset --local. Preserva los datos de cualquier instancia local preexistente. No enlazar el proyecto cloud ni ejecutar migraciones remotas en esta fase.
3. Implementa la API y conecta la interfaz de la demo. Conserva la exploración pública. Usa un selector local de perfiles semilla con sesión de servidor para probar sin registro. Retira el estado de negocio de localStorage una vez conectados los flujos. Implementa preferencias, búsqueda, agenda, métricas, reserva, cancelación por fecha y lista de espera conforme al plan.
4. Implementa el checkout con precio calculado en servidor, retención de 10 minutos y transacciones para evitar doble reserva y exceso de aforo. El adaptador de pago falso debe permitir éxito, fallo y caducidad y procesar reintentos sin duplicar cobros simulados ni reservas. Prepara el contrato del proveedor para Stripe posterior. La base ya debe admitir identidades reales futuras.
5. Implementa solicitudes unidireccionales según el plan. Solo el profesional puede enviar al cliente o al gestor del espacio relacionado con su reserva. El destinatario solo lee la solicitud. Comprueba esa restricción también en el servidor y elimina el chat anterior.
6. Aplica los controles del plan para autorización por objeto, sesión, CSRF, validación, consultas parametrizadas y separación de secretos. El servidor debe rechazar la configuración de producción si están habilitados los perfiles o pagos de prueba. Añade y ejecuta pruebas de integración de permisos y concurrencia, además de los recorridos completos del plan. Comprueba que una reserva pagada en modo falso sigue visible después de reiniciar la aplicación.
7. Deja en el README los comandos exactos de instalación, arranque, migraciones y seeds, pruebas y reinicio local. Entrega el listado de cambios, resultados comprobados y cualquier bloqueo real con su causa. Si Docker u otro requisito local falla, diagnostícalo, termina el trabajo independiente y distingue qué pruebas quedaron pendientes. La fase termina cuando el flujo funciona desde un clon limpio con datos semilla.
~~~
